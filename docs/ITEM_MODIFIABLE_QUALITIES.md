# Item-Modifiable Qualities Catalog

## Purpose

This is the canonical inventory of gameplay qualities that items and abilities
may target. It supports item design, schema design, modifier registration, test
coverage, and the future item creation application.

The catalog is intentionally extensible. "Modifiable" does not mean that every
value is exposed immediately, or that every combination is automatically safe.
Each implemented quality needs:

- a stable property identifier;
- a declared value type and valid range;
- a selector describing what it targets;
- an ordered operation such as add, multiply, clamp, or replace;
- an authored lifetime and ownership scope;
- deterministic tests and player-facing description text.

## Governing Rules

1. Item definitions and policies are immutable after loading. Runtime systems
   modify compiled values, owned state, or explicitly exposed active-effect
   properties.
2. Persistent item modifiers compile in acquisition order. Each item applies to
   the result produced by the items before it.
3. Base class values, persistent equipment values, and per-life runtime effects
   remain distinguishable even when they contribute to one effective result.
4. Numeric values may change immediately when their owning policy permits it.
   The fundamental nature of an existing policy does not silently change.
5. Selectors can target one property, tag, damage type, local portion ID,
   equipped slot, source, target, active-effect instance, or qualifying spatial
   set.
6. Positive and negative modifications use the same system. A player-facing
   "weakness" is a negative resistance modifier, not a separate engine.
7. Items never equip or replace themselves during combat. Equipment changes
   occur only in the selection phase.
8. The game has no universal stamina or mana values. Item-specific cooldowns,
   charges, counters, and costs remain allowed.

## Implementation Status

- **Implemented:** the base quality exists in the current playable slice.
  This does not imply that item-driven modification is wired into it yet.
- **Designed:** behavior has an accepted architecture but is not necessarily
  connected to item compilation yet.
- **Candidate:** useful extension point that still needs explicit design before
  implementation.

## Values That Items Must Not Directly Modify

These are infrastructure or stable identities rather than gameplay qualities:

- server authority or which peer is allowed to decide outcomes;
- protocol version, serialization format, packet cadence, or simulation tick
  rate;
- immutable item-definition identity and authored policy type;
- active-effect instance IDs, combatant IDs, source-life IDs, or stable local
  damage-portion IDs;
- the damage type or tags of an already-existing portion unless a declared
  conversion phase creates/replaces portions according to policy;
- ticks that have already executed;
- historical immutable damage, healing, overkill, or trigger results;
- equipment ownership during combat;
- universal stamina or mana, because those systems do not exist.

## Catalog Maintenance Checklist

When introducing a new modifiable quality:

- [ ] Add it to the appropriate table with its status.
- [ ] Assign a namespaced stable property identifier.
- [ ] Define its numeric unit, range, precision, and integer-tick conversion.
- [ ] Define valid operations and acquisition-order behavior.
- [ ] Define valid selectors and ownership/lifetime scopes.
- [ ] Define compilation-time and runtime validation.
- [ ] Define multiplayer replication or deterministic recomputation needs.
- [ ] Add positive, negative, boundary, stacking-order, and serialization tests.
- [ ] Add exact player-facing description formatting.
- [ ] Add it to the item creation application's property registry.
